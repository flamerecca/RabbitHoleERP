# RabbitHoleERP

RabbitHoleERP 是一套以 Laravel 打造的練習用 ERP 系統，模擬進銷存與退貨相關業務。這個 Repository 的目的不是產出一套完整可上線的產品，而是刻意模擬「維護 Legacy 專案」時常見的困境，讓開發者在近似真實的條件下練習如何安全地閱讀、修改與擴充一套自己不熟悉的舊系統。

## 這是一個什麼樣的練習

實務上維護 Legacy 專案時，最常遇到的不是「技術難度」，而是資訊不足帶來的不確定性：

- **文件缺失或過時**：`docs/` 資料夾已被加入 `.gitignore`，不會出現在這個 Repository 中。你手上能看到的只有 Source Code、Migration、Route 與測試，跟現實中接手舊專案時常見的狀況一致。
- **測試不足或錯誤**：現有測試覆蓋率低，業務功能完全沒有測試，詳見[為什麼只保留部分測試](#為什麼只保留部分測試)。部分測試可能只是骨架，甚至有測試本身邏輯有誤，無法完全信任「測試綠燈 = 行為正確」。
- **程式碼雜亂、缺乏一致慣例**：命名、分層、驗證方式等可能不一致，需要自己從程式碼歸納出目前專案實際遵循的慣例，而不是假設它遵循某套教科書式的最佳實踐。

## 為什麼只保留部分測試

`tests/` 目前只保留 Laravel Starter Kit 內建的測試，涵蓋登入註冊、個人設定與團隊管理這些框架附帶的功能。進銷存、退貨等業務功能的測試已刻意排除，不會出現在這個 Repository 中。這樣安排有兩個原因：

- **模擬真實的接手情境**：許多 Legacy 專案的測試只停留在專案初始化時框架附帶的那幾支，真正的業務邏輯反而沒有任何測試。在這種專案裡，CI 綠燈只代表登入註冊沒壞，不代表核心業務正確。
- **讓「補測試」成為練習本身**：如果直接提供業務測試，等於把系統預期行為的答案攤開。你需要自己從 Source Code、Migration 與 Route 推敲現有行為，再把它寫成測試，這正是下方「建議的應對方式」第 2 點要練習的能力。

保留下來的 Starter Kit 測試可以用來確認開發環境是否建置正確，也可以當作撰寫新測試時的格式參考。

> [!IMPORTANT]
> `.gitignore` 以白名單方式只追蹤這些 Starter Kit 測試，`tests/` 底下新增的檔案預設都會被 Git 忽略。在自己的 Fork 中練習補測試時，請先刪除 `.gitignore` 中 `# Only the starter kit tests are published` 這一段規則，否則新寫的測試無法 commit。

## 建議的應對方式

在資訊不足的情況下修改系統，核心原則是「先建立安全網，再動手」：

1. **先讀懂再動手，用工具還原上下文**：善用 `php artisan route:list`、`database-schema` 等工具，從 Route、Model、Migration 反推目前系統實際的行為與資料結構，不要只憑檔名或註解猜測。
2. **補測試而不是先改功能**：在修改任何邏輯之前，先為現有行為補上測試，把它當作「這支程式現在做了什麼」的紀錄。有了這層安全網，之後重構或修 Bug 才敢放心下手。
3. **發現一個慣例，就記錄一個慣例**：讀程式碼時歸納出的命名方式、分層方式、驗證方式等，隨手記下來，避免下次又要重新摸索一次，也讓後續的修改保持一致。
4. **小步前進，頻繁驗證**：每次改動範圍盡量小，改完就跑對應測試，而不是累積一大包修改後才一次驗證，降低「壞掉了卻不知道是哪一步造成的」風險。
5. **區分「修 Bug」與「順手重構」**：修正一個錯誤時，先只做最小必要的修改讓測試通過，不要同時進行大範圍重構，避免把兩件事混在一起導致難以 Review 與還原。
6. **保留刻意的不確定性**：遇到看不懂或看似不合理的程式碼，不要急著刪除或改寫，先假設它背後可能有你還不知道的業務原因，透過測試或詢問確認後再處理。

## 環境需求

- PHP 8.5
- Laravel 13
- Node.js，用於前端資源建置

## 開發指令

```bash
composer install
npm install
php artisan migrate

# 開發時同時啟動 Server、Queue、Vite
composer run dev

# 執行測試
php artisan test --compact
```
